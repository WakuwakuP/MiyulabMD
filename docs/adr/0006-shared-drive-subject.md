# 0006. 共有ドライブはユーザーではなくドライブを主体にする

- ステータス: 採択
- 日付: 2026-10-19（設計合意時点。実装前）
- 関連: `CONTEXT.md`（共有ドライブ / 主体 / メンバーのみ / 主体をまたぐ移動）、`docs/design.md` §7.2 / §12

## コンテキスト

フォルダもノートも `owner_id` がユーザーを指し、共有はマイドライブ上の grant
（共有フォルダ）である。作った人が抜けると中身も去る。残したい資料の置き場として、
ユーザーを所有者にしない根が要る。

`owner_id` はフォルダパスの一意性やスペース、メダリオン、採番の名前空間にも
なっている。主体をドライブに変えると、この名前空間と「所有者だけが管理できる」
という権限判定の両方を戻すことになる。

## 決定

- 共有ドライブの主体はドライブ自身とする。メンバーが抜けてもノートとフォルダは残る。
  共有フォルダの別名にはしない。
- 既存の `owner_id` 名前空間を流用する。マイドライブではユーザー ID、共有ドライブでは
  共有ドライブ ID。種別は `owner_kind`（`user` | `shared_drive`）。ドライブ ID を
  入れるための偽ユーザーは作らない。`notes.owner_id` の `users` 外部キーは外す。
- 中身はメンバーのみ。公開範囲、リンク共有、個別 grant、共有ページは使わない。
  `owner_kind = shared_drive` のアクセス判定はメンバー役割だけを見る。
- 役割はドライブ全体に一つ（管理者 / 編集者 / 閲覧者）。フォルダごとの役割は置かない。

## 検討した代替案

- 共有フォルダのまま運用する → 所有がユーザーのままなので、退会で中身が去る問題が
  残るため不採用。
- ドライブごとに偽の `users` 行を作り、既存の外部キーを維持する → 主体がユーザーに
  見え、ログインや設定と混ざるため不採用。
- マイドライブと同じ公開範囲と grant をドライブ内でも使えるようにする → メンバー以外へ
  漏れる経路が増え、画面の「共有」と共有ドライブの境界が再び曖昧になるため不採用。

## 影響

- 主体をまたぐ移動は、今の「別のドライブへは移動できません」を置き換える。ノート ID と
  Yjs の部屋は変えず、`owner_id` だけを移す。スペースルートと採番スコープの根は、
  割当を解くまで拒否する。
- 共有ドライブ内のスペース、メダリオンセット、命名規則、記事ソース、採番カウンタは
  ドライブの名前空間に属する。個人のものは混ざらない。
- 共有ドライブのノートはオフライン編集資格を持たない。表示キャッシュでの閲覧は今のまま。
