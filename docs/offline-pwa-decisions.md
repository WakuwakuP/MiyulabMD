# PWA・オフライン閲覧：意思決定と検証の記録

機能の現在の契約は [仕様書](offline-pwa.md)、実装候補は
[レビュー資料](../review-artifacts/README.md) を参照する。
本書は選択肢・採用理由・結果・見直しを残す台帳であり、記載された方針が
すべて実装済みであることを意味しない。

## 運用ルール

ユーザーの最新指示により、実装上の問題は原則として推奨案を選んで進める。
以前の「問題発見時に停止して選択を待つ」という進め方を置き換える。
選択が後で不適切と判明した場合の手戻りも許容されている。

- 判断ごとに、背景、選択肢、選んだ案と理由、影響・制約、検証、状態を記録する。
- 方針を見直すときは古い判断を消さず、何が分かったかと後継の判断を追記する。
- サブエージェントの判断も候補内の `decisions.md` に残し、親が本書へ集約する。
- 方針選択前の状態と、選択・実装・検証の区切りをローカルコミットに残す。
- WIP、RED テスト、未採用候補を含むチェックポイントは、その旨を明示する。
- ユーザー不在時に署名が失敗するため、エージェントの今後のcommitには
  `--no-gpg-sign`を指定する。ユーザー・リポジトリ全体の署名設定は変更しない。
- コミットの記録は履歴の強制書き換えや外部公開の許可ではない。破壊的操作、
  ワークスペース外への影響、外部送信など、別途確認が必要な操作は確認する。
- 実装完了時に、採用方針、棄却・見直し、検証結果、残る制約を整理して報告する。

## R01：削除失敗で権限拒否が消える問題

- **背景**：API が403を返しても、IndexedDB の削除が失敗すると後の通信失敗で
  同じ本文が再表示された。親が実 Chromium で再現した。
- **選択肢**：A＝論理的な拒否記録と物理削除を分離、B＝ユーザー全体の利用停止。
- **選択**：A。通常の権限拒否では、そのノートだけを非表示にできるため。
- **制約**：拒否記録自身の永続化が失敗した場合は、ユーザー単位の実行中キャッシュを
  安全側へ停止する。すべての書き込みが拒否される場合の再起動後までの保証はできない。
- **検証**：`note-read-denial.spec.ts`、`note-denial-failure.spec.ts`。
- **結果**：方針維持。単純に削除失敗を握りつぶす候補は棄却。R02・R04で停止処理を補強。

## R02：DBを開けないと拒否処理を飛ばす問題

- **背景**：拒否応答後に DB open が失敗すると、optional cache の `null` として扱われ、
  警告も利用停止も行われなかった。ストレージ復旧後に本文が復活した。
- **選択肢**：A＝拒否入口をDB接続から独立させる、B＝その画面のキャッシュ全体を止める。
- **選択**：A。ユーザー分離と正常なオンライン閲覧を維持する。
- **必要条件**：対象ユーザーとノートを接続前に把握する。既存・新規ハンドルに停止を適用し、
  I/Oが再び成功しただけでは自動再開しない。HTTP拒否結果と `cacheWarning` を返す。
- **検証**：`note-denial-failure.spec.ts` の DB-open failure。
- **結果**：方針維持。開始時だけの停止チェックでは不足し、R04へ続く。

## R03：遅い成功応答が新しい拒否を取り消す問題

- **背景**：先に開始したAの200応答を遅延させ、Bの403完了後にAを完了させると、
  本文保存・禁止解除でキャッシュが復活した。親が実 Chromium で確認した。
- **選択肢**：A＝ユーザー・ノート単位で拒否前後の要求を区別、
  B＝一度拒否したノートは手動クリアまで自動復帰しない。
- **選択**：A。古い要求を無効にしつつ、権限再付与後の新しい取得で自然に復帰できる。
- **必要条件**：セッション作成時でなく各要求の開始時を基準とする。
  保存・禁止解除・ネットワーク／キャッシュ結果の最終返却に一貫して適用する。
  自分の拒否処理が世代を進めたことだけで、HTTP拒否結果まで隠さない。
- **検証**：`note-denial-ordering.spec.ts` の遅い200と進行中キャッシュ読み取り。
- **結果**：最終ガードを取得直後に置く案は不十分。全awaitの後、成功結果の返却直前へ修正。
  それでもユーザー全体の停止は別ノートへ伝わらず、R04で共通化する。

## R04：ユーザー停止が進行中処理・フォルダ・一覧へ伝わらない問題

- **背景**：v6候補は親のブラウザテスト25件を通過したが、独立レビューで次の不足が判明。
  - 利用停止前に本文読み取りを開始すると、停止後に古い本文を返し得る。
  - 別ノートの拒否記録保存失敗によるユーザー全体の停止を、ノート単位の世代では検出できない。
  - フォルダ読み書き・一覧保存に停止チェックがなく、一覧読み取りにも終端チェックがない。
  - 保存や禁止解除が開始時の判定を通過済みの場合、停止との競合を保護できない。
- **選択肢**：A＝ユーザー単位の共通ライフサイクルを全キャッシュ操作へ適用、
  B＝その画面の全ユーザーのオフラインキャッシュを停止。
- **選択**：A。他ユーザーへの影響を避け、決定済みのユーザー分離を維持する。
- **必要条件**：開始時と終端の判定、未確定トランザクションの取消、
  本文・フォルダ・一覧・禁止解除の一貫した管理。確定済みコミットを失敗扱いに
  変えたり、参照済みファイルを削除したりしない。正常なオンライン表示は維持。
- **検証**：`user-cache-suspension.spec.ts` の open／commit failure 2ケースを親が追加。
  旧候補に対して両方REDを確認。候補専用ランナーの既定対象は計27件。
- **結果**：実装中。v7は27件通過の報告があったが、候補保存に失敗したため採用不可。
  新方式の `user-cache-suspension-v8` で改めて実装・検証する。

## R05：テスト済みコードの受け渡しを失う問題

- **背景**：実装・コピー・復元の間に、候補の消失、原本復元の不一致、
  baselineを候補として保存する事故が繰り返された。v7でもテスト済み候補が残らなかった。
- **選択肢**：A＝候補専用ファイル自体を直接編集・検証、
  B＝未採用コードをライブ作業ツリーへ残し、親がレビュー・復元。
- **選択**：A。レビュー前のライブ反映を避けながら、危険なコピー・復元工程をなくす。
- **実装**：`apps/web/scripts/check-offline-candidate.mjs`。
  ブラウザは候補をViteで差し替える。TypeScript7の旧compiler APIがないため、
  型チェックは候補と同じbytesを検証専用ツリーへ一方向に配置してnative CLIで実行する。
  候補やライブソースへ書き戻さない。Biomeは候補を直接検査する。
- **検証**：候補の型チェック・Biome成功、候補にだけ入れた型エラーの検出、
  旧候補の停止テスト2件がREDになること、検証前後の元ソース・候補不変を確認。
- **制約**：テスト前後のハッシュと結果を記録し、検証後にコードを変えたら再検証する。
  旧資料には不一致があり得るため、過去の「passed」を新候補の証拠に流用しない。
- **状態**：導入済み。チェックポイント `9d7f11f` に保存。v8へ適用中。

## D21：v8のユーザーライフサイクル管理候補

- **状態**：候補内で選択後、独立レビューで不採用。D22へ見直し。
- **選択前チェックポイント**：`0f960ec`。
- **背景**：R04で決めたユーザー全体の停止を、進行中の処理にも適用する必要がある。
- **候補が検討した案**：操作開始時だけの停止チェック、ユーザーごとの寿命世代を

## D22：未確定操作の取消と確定済みデータの保護

- **状態**：推奨案を選択、回帰テスト追加・実装へ進む。
- **選択前チェックポイント**：`0f960ec`。v8候補・レビュー結果・本判断を`e7df645`に保存。
- **背景**：D21のepoch終端チェックだけでは書き込みの発生自体を防げず、
  commit後の検査失敗が参照中の本文削除につながる。禁止解除にも同じ停止管理が不足。
  直接の本文読み取りと一覧の最終返却にも判定漏れがある。
- **選択肢A**：ユーザー寿命にひもづく未確定操作の取消と、実トランザクションの
  complete／abort判定を共通化。完了済みcommitのファイルは削除しない。
  キャッシュの返却直前にはユーザー寿命・必要な拒否世代を確認する。
- **選択肢B**：全キャッシュ操作をユーザー単位のキューへ直列化する。
  順序は追いやすいが、遅い読み取りの後ろで拒否処理が待つ問題と、操作間の遅延を増やす。
- **選択肢C**：完了後のepochチェックだけを増やす。
  表示の抑止には使えても、既に行われた書き込み・禁止解除や誤cleanupは防げない。
- **採用**：A。保存の事実と表示可否を分け、不要な直列化を避けながら既存の
  commit-terminalルールを全キャッシュ操作へ適用できるため。
- **影響・制約**：オンラインの正常応答はキャッシュ取消と切り分けて維持。
  実際にcommitが完了した後の停止は、そのcommitを巻き戻したことにしない。
  ブラウザ再起動後や複数タブ全体の停止保証は、この同一runtimeの修正とは別。
- **検証**：`user-cache-write-lifecycle.spec.ts`を追加し、v8に対して親が実行。
  native IndexedDBの未確定／complete境界で停止させた両ケースがRED。
  未確定時は旧本文、complete時は新本文が必要だが、両方とも再起動後に本文が読めなかった。
  実行コマンド：
  `node apps/web/scripts/check-offline-candidate.mjs review-artifacts/user-cache-suspension-v8 browser user-cache-write-lifecycle.spec.ts`
  （exit 1、2 failed）。後継候補の既定検証は既存27件＋この2件の計29件。
- **見直し元**：[v8レビュー結果](../review-artifacts/user-cache-suspension-v8/parent-review.md)。

## D23：エージェントのチェックポイントを署名なしで保存

- **状態**：ユーザー承認により選択、今後のcommitへ適用。
- **選択前チェックポイント**：`03c4d37`。
- **背景**：ユーザー不在時に署名付きcommitが失敗するため、
  署名を外してcommitしてよいと明示された。
- **選択肢**：A＝各commitに`--no-gpg-sign`を指定、
  B＝リポジトリまたはユーザー全体の署名設定を無効化。
- **採用**：A。エージェントの操作だけに限定し、ユーザーの通常の署名設定を維持する。
- **制約**：既存commitの署名や履歴は書き換えない。pushや公開の追加許可ではない。
- **実行ルール**：`GIT_EDITOR=true git commit --no-gpg-sign ...`を使い、
  Gitの書き込み操作を並列・重複実行しない。
- **実行上の記録**：直前のチェックポイント作成では親がcommitコマンドを
  重複送信し、一方がindex.lock競合で失敗した。成功済み`03c4d37`と
  cleanな作業ツリーを読み取り専用コマンドで確認し、ロックファイルは削除していない。
